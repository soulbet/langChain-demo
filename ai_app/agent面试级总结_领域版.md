## 1. Agent 的定义与本质

**Agent（智能体）= LLM（大脑）+ 工具（手脚）+ 记忆（经历）+ 循环决策（工作方式）**。

- **LLM**：理解与推理，是"决策中枢"。
- **工具 Tool**：让 Agent 具有**行动能力**（查库、调 API、跑代码、读写文件）——这是 Agent 区别于纯 Chat 的核心。
- **记忆 Memory**：跨轮次记住上下文，让 Agent"有连续性"。
- **循环 Loop**：`观察(Observe) → 思考(Reason) → 行动(Act) → 再次观察...直到完成`。

**与纯 LLM 的本质区别**：
> 纯 LLM 只**输出文本**；Agent 会输出**动作指令**（`tool_calls`）并进入"执行 → 回填 → 再决策"的循环，直到得到最终结果，因而能**真正做事**。

**Agent 的"智能"来源**：模型的能力（推理/生成） + 行动接口（工具）+ 反馈闭环（观察结果修正决策）。

## 2. Agent 的核心组成

| 组成 | 作用 | 常见实现 |
|------|------|---------|
| **大脑（Model）** | 推理、规划、决策 | 大语言模型（LLM）或推理模型 |
| **感知（Perception）** | 接收外部信息 | 检索、视觉/语音/传感器、RAG |
| **行动（Action）** | 改变世界 | 函数调用、API、代码执行、文件/数据库操作 |
| **工具（Tool）** | 行动的具体接口 | `@tool` / `Function` / MCP 工具 |
| **记忆（Memory）** | 存历史、经验、事实 | 会话缓存、向量库、DB |
| **规划（Planning）** | 拆解/排序/评估任务 | 任务分解、子目标、计划生成 |
| **观测（Observation）** | 反馈回路 | 工具返回内容、执行结果、错误信息 |

**Agent 的"四性"**：自主性（自主决策）、行动性（能调用工具）、目标导向（围绕目标）、环境交互（感知-行动闭环）。

## 3. Agent 的经典范式 / 推理模式

### 3.1 按"推理-行动"耦合方式
| 范式 | 做法 | 特点 |
|------|------|------|
| **ReAct** | 交替 `Thought → Action → Observation` | 灵活自然；工具调用是内生的 |
| **Plan-and-Execute / ReWOO** | 先规划出完整计划（不执行），再统一/逐条执行 | 减少重复推理、节省 token；但计划可能错 |
| **Plan-then-Act** | 先拆解子目标，再逐目标执行 | 适合长任务 |
| **Executor / Planner** | 规划器（planner）+ 执行器（executor）分离 | 模块化、可替换 |

### 3.2 按"自我改进"方式
| 范式 | 做法 | 特点 |
|------|------|------|
| **Self-Refine** | 生成 → 自我反馈 → 修正（多轮） | 提升质量，成本↑ |
| **Reflexion** | 失败后把"教训"写入记忆，下次避免 | 跨轮学习 |
| **CRITIC** | 用外部工具/验证器自我批判 | 减少幻觉 |
| **Tree of Thoughts（ToT）** | 多分支搜索 + 回溯 | 推理深但开销大 |
| **Self-Consistency** | 多次采样取多数 | 提可靠、成本↑ |

### 3.3 按"是否用工具/代码"
- **纯文本推理**（CoT 内化）：不调工具，靠推理。
- **外部工具**（调用函数/API）。
- **代码即工具**（生成代码并执行）：灵活，但需要沙箱。

> 面试常问：**循环必须有终止条件**（步数上限 / `recursion_limit` / 结果达标 / 人工介入），否则会死循环、烧钱。

## 4. 工具调用 Tool / Function Calling

### 4.1 什么是工具
- 工具把"能力"暴露给模型，模型按 **schema** 决定何时调用、传什么参数。
- 一次调用流程：
```
模型输出 tool_calls（工具名 + 参数 JSON）
  → 框架执行工具
  → 得到 ToolMessage / 结果
  → 回填给模型
  → 模型基于结果继续推理
  → ...直到给出最终答案
```

### 4.2 工具描述（Schema）写得好的关键
- **参数类型**：描述每个参数的含义/可选/取值范围；
- **何时用**：明确"什么情况该调用、什么情况不该"；
- **异常说明**：工具返回错误时如何处理（重试 / 降级 / 让模型重新调用）。

### 4.3 工具相关的常见设计问题
| 问题 | 对策 |
|------|------|
| 工具太多，选择困难 | 工具选择/路由、分层分组、`tool_choice` 强制 |
| 工具参数写错 | 校验/修正参数、工具失败重试 |
| 工具返回太长 | 截断、摘要、只保留结构化结果 |
| 模型不支持工具 | 用结构化输出 / 推理模型 / 文本约定 |
| 工具能引发副作用 | 危险操作加确认（HITL）、最小权限、幂等设计 |
| 工具错误处理 | 捕获异常、分类重试、统一降级 |

### 4.4 Function Calling vs Tool Calling
- 概念相近：都让模型输出结构化调用。
- 区别：**Function Calling** 偏老（OpenAI 早期），**Tool Calling** 更通用、支持多种 schema 与并行调用；现代平台多用 tool schema（可含 `strict` 强约束）。

## 5. 记忆 Memory

### 5.1 记忆的分类
| 类型 | 说明 | 实现 |
|------|------|------|
| **短期/工作记忆** | 当前会话内的消息 | messages 直接回填 |
| **长期记忆** | 跨会话持久化 | DB / 向量库 / 对象存储 |
| **情景记忆（Episodic）** | 个人经历 | 历史对话/事件 |
| **语义记忆（Semantic）** | 事实/知识 | 知识库、向量检索 |
| **程序记忆（Procedural）** | 做事的方法 | 技能、偏好、规则 |

### 5.2 记忆的工程实现
- **滑动窗口**：只保留最近 N 条消息；
- **摘要记忆**：超长时总结历史，压缩上下文；
- **向量记忆**：把历史/知识向量化，按相关度检索回填；
- **实体/关系记忆**：用图 / 结构化存储保持事实一致；
- **持久化**：checkpointer（会话断点）、Redis/Postgres、文件。

### 5.3 记忆的关键权衡（面试高频）
> **上下文太长** → 烧 token、可能丢失关键信息（"迷失在中间"），需要**压缩/检索/剪枝**。
> **记忆太长** → 成本高；但太短 → 丢上下文。要做"**记忆分层**"：最近消息 + 相关历史 + 长期知识。

## 6. 规划 Planning

### 6.1 规划解决什么
把**复杂/长程任务**拆解为可操作、可排序、可验证的子步骤。

### 6.2 常见规划方法
- **任务分解**：一次拆成子任务（todo list），逐个完成；
- **计划生成 + 执行**：先生成完整计划，再执行；
- **逐步规划 + 修正**：边做边调整（Reflection）；
- **启发式 / 检索式规划**：从历史相似任务索引计划（few-shot planning）。

### 6.3 规划的关键点
- **子目标一致性**：子任务是否服务于总目标；
- **依赖与顺序**：哪些子任务有先后/并行；
- **失败重规划**：子任务失败时如何回退/改写计划；
- **成本控制**：规划本身消耗 token；不要过度拆分。

## 7. 多智能体系统 Multi-Agent

### 7.1 为什么需要多 Agent
- **复杂任务**：单个 Agent 上下文/能力受限；
- **专业化**：各 Agent 各司其职，效果好；
- **分工与并行**：同时处理、提升吞吐；
- **协作/对抗**：互相校验、辩论，提高可靠性与质量。

### 7.2 主流拓扑
| 拓扑 | 描述 | 适用 |
|------|------|------|
| **Supervisor（主管）** | 一个调度 Agent 把任务分给子 Agent 并汇总 | 可分解、需分工 |
| **Hierarchical（层级）** | 主管→组长→组员，多层 | 大规模、强治理 |
| **Router（路由）** | 按意图路由到不同专家 Agent | 意图清晰、互不重叠 |
| **Sequential（串行）** | 前一个输出喂给下一个 | 流水线 |
| **Parallel（并行）** | 同时跑多个，最后汇总 | 可并行子任务 |
| **Network（网络/竞争）** | 互相通信/辩论 | 复杂协作、评估/生成对抗 |
| **Swarm（群体）** | 动态协商、自我组织 | 高度动态、去中心化 |

### 7.3 多 Agent 的核心难点
- **上下文共享/传播**：子 Agent 需要多少上下文？太多烧 token、太少丢信息；
- **通信协议**：如何传消息/结果/控制权（结构化消息、`Command`、事件总线）；
- **信任与治理**：子 Agent 权限最小化、身份、审计；
- **故障恢复**：子 Agent 挂了谁接管？超时/重试/降级；
- **一致性**：多个 Agent 对同一实体/数据的认知一致（共享状态、去重）；
- **成本**：多 Agent = 多次模型调用，成本与时延显著增加。

### 7.4 Agent 间通信（协议层面）
- **结构化消息**：Task / Result / <agent, message>；
- **控制权移交**：supervisor 把 `task → agent`，agent 完成后 `result → supervisor`；
- **共享状态**：全局状态、黑board、store；
- **标准协议**：MCP（工具/数据接入）、A2A / Agent 间协议（跨 Agent 协作）、IPC。

## 9. RAG 与 Agent 的关系

- **RAG Agent**：把"检索"作为 agent 的一种工具/动作。
- 标准 RAG：`Embedding → 检索（向量/关键词/混合）→ 上下文拼装 → LLM`。
- **Agentic RAG**：Agent 自主决定"要不要检索、检索什么、是否多跳、是否重试"，而非固定一次检索。
- 关键组件：
  - **混合检索**：向量（语义）+ 关键词（BM25），用 **RRF** 融合；
  - **精排 Reranker**：CrossEncoder 提高准确率；
  - **查询改写/多跳**：改写问题、拆多跳问题、伪答案检索。
- **RRF vs Reranker**（高频）：RRF 负责多路召回融合、**提高召回率**、只看排名、无需训练；Reranker 负责相关性精排、**提高准确率**、真正理解查询-文档、但**慢且贵**。

## 10. 执行环境与安全（沙箱 / 权限）

当 Agent 要**跑代码 / 执行命令 / 操作文件**时，必须隔离。

### 10.1 为什么需要沙箱
- **隔离**：防止 Agent 任意代码破坏宿主；
- **安全**：防密钥泄露、越权访问、网络外联；
- **可复现**：受限、可重置的执行环境；
- **资源限制**：CPU/内存/时间/网络。

### 10.2 常见沙箱策略
- **主机执行（最弱）**：直接跑，仅用于信任环境；
- **容器/Docker**：隔离 OS 层；
- **受限代码解释器**：如受限 Python/JS 运行时（限制 import/网络/时间）；
- **云端沙箱**：托管受限执行；
- **虚拟文件系统**：只允许访问指定目录。

### 10.3 安全设计要点
- **最小权限工具**：只暴露必要的能力；
- **危险操作二次确认（HITL）**：写库/删文件/发邮件等；
- **密钥管理**：密钥只走环境变量/Secret，绝不硬编码；
- **审计**：记录工具调用、输入输出、时间、Agent 身份；
- **超时与限制**：执行超时、步数上限、预算上限。

## 11. 状态、持久化与中断恢复

Agent 往往需要**跨轮/跨会话**保状态。
- **会话/线程**：用唯一 `thread_id`/`session_id` 标识一场对话；
- **检查点（checkpoint）**：保存每个 step 的状态（消息、变量、工具结果），支持：
  - **记忆恢复**：同一线程再次进入，能续上上下文；
  - **断点续跑**：中断后从某步继续；
  - **时间旅行**：回看/回放历史状态（调试）；
- **状态结构**：通常是 `TypedDict`，字段用 `Annotated[type, reducer]` 定义"如何合并"（追加/覆盖/累加）；
- **中断/人工介入（HITL）**：在关键节点 `interrupt` 暂停，等人审结果再 `resume` 继续。

## 12. 可观测与评测

### 12.1 可观测（Observability）
- **追踪（Tracing）**：一条请求 = 一棵 trace 树（`parent_run_id` 级联），记录每一步（模型/工具/检索/错误）；
- **指标**：`ttfb`（首 token 时延）、总时延、`input/output_tokens`、工具调用成功率、重试/降级率、缓存命中率、错误率；
- **归因**：按 `run_id`、`tag`、`metadata`、团队/版本维度聚合；
- **工具**：LangSmith / LangFuse / 自研 + 结构化日志。

### 12.2 评测（Evaluation）
| 层面 | 指标 |
|------|------|
| **任务** | 任务成功率、完成度、步骤效率 |
| **工具** | 工具调用准确率、参数正确率、时效 |
| **RAG** | 召回率、MRR、NDCG、答案正确性 |
| **对话/生成** | 有用性、事实一致性、相关性、安全 |
| **成本/性能** | token、时延、成本、兜底率 |
| **对抗** | 幻觉、提示注入、边界用例 |

> 评测方法：离线基准集 + 在线指标 + 人工标注 + LLM-as-judge（用强模型打分）+ A/B。

## 13. 安全、幻觉与对齐

### 13.1 幻觉（Hallucination）
- 模型编造不存在的"事实"。
- 缓解：RAG（检索增强 + "资料不足就承认不知道"）、结构化输出、精排、更明确约束、引用溯源、验证工具。

### 13.2 提示注入（Prompt Injection）
- 恶意/不可信文本里嵌入指令，诱导 Agent 违规。
- 缓解：数据与指令定界 + 声明忽略其中指令、工具最小权限、危险操作确认、输出过滤、信任边界建模。

### 13.3 越权 / 数据安全
- 工具权限过大 → 越权读写；
- 缓解：RBAC/ABAC、最小权限、审计、脱敏（PII）、安全沙箱。

### 13.4 对齐（Alignment）
- 让 Agent 行为符合人类意图与价值观；
- 手段：`system prompt` 约束、`rubric`/自评、奖励模型、RLHF、护栏（guardrails）、输出校验。

## 15. 关键词大表

| 关键词 | 含义 |
|--------|------|
| **Agent** | 智能体：LLM+工具+记忆+循环 |
| **LLM** | 大语言模型，Agent 的"大脑" |

## 16. 高频面试题速答

**Q1：Agent 和纯 LLM 的区别？**
> 纯 LLM 只输出文本；Agent 会输出 `tool_calls` 并进入"调用工具→回填→再决策"的循环，能真正行动、多步完成任务。

**Q2：ReAct 是什么？**
> 边推理边行动：Thought → Action → Observation，循环直到得出答案。是多数 Agent 的默认内核。

**Q3：工具调用怎么实现？**
> 用 JSON Schema（从函数签名/docstring 生成）描述工具；模型按 schema 输出结构化参数；框架执行并把结果回填给模型继续推理。

**Q4：工具描述怎么写才好？**
> 明确"参数含义、何时用/何时不用、出错怎么办"；描述越清晰，模型调用越准。

**Q5：Agent 记忆力怎么设计？**
> 分层：最近消息（滑动窗口）+ 相关历史（检索）+ 长期知识（向量/DB）；结合摘要与剪枝控制成本；用 checkpointer 持久化。

**Q6：如何减少幻觉？**
> RAG 检索增强 + "资料不足就承认不知道"；精排（Reranker）；结构化输出；引用溯源；验证工具；明确约束。

**Q7：RRF 和 Reranker 区别？**
> RRF 融合多路召回、只看排名、提召回率、无需训练；Reranker 理解相关性、精排、提质、但慢且贵。

**Q8：多 Agent 有哪些拓扑？**
> Supervisor、Hierarchical、Router、Sequential、Parallel、Network（辩论）、Swarm。难点在上下文/信任/故障恢复/一致性/成本。

**Q9：多 Agent 如何通信/移交控制权？**
> 结构化消息（Task/Result）、共享状态、事件总线；协议层 MCP（工具数据）、A2A（跨 Agent）；控制权用 `Command`/supervisor 调度。

**Q10：Agent 会死循环怎么办？**
> 步数上限/`recursion_limit`、调用限流、todo 清单、终止条件、结果达标、人工介入。

**Q11：如何保证 Agent 安全？**
> 沙箱隔离、最小权限工具、危险操作 HITL、密钥管理、审计、超时与预算、提示注入防御、PII 脱敏。

**Q12：如何评测一个 Agent？**
> 任务成功率、工具调用准确率、RAG 召回/NDCG、答案正确性/一致性、成本/时延；离线基准 + 在线指标 + LLM-as-judge + A/B。

**Q13：为什么需要多 Agent 而不是一个大 Agent？**
> 复杂任务上下文受限、需要专业化/分工/并行/互相校验；但成本、通信、故障恢复也随复杂度上升，需权衡。

**Q14：RAG 和 Agent 怎么结合？**
> RAG 提供"事实/知识"，Agent 提供"决策/行动"；Agentic RAG 让 Agent 自主决定检索什么、是否多跳、是否重试。

**Q15：Agent 的成本怎么控制？**
> 缓存、轻量模型顶替、跨供应商 fallback、熔断+兜底话术、限制调用步骤、摘要压缩上下文、预算护栏。

## 17. 一页带走

- **Agent = LLM（大脑）+ 工具（手脚）+ 记忆（经历）+ 循环（工作方式）**。
- **四大范式**：ReAct / Plan-and-Execute / Reflection / Multi-Agent。
- **两条主线**：
  - **能力**：工具、RAG、记忆、规划、多 Agent、沙箱、MCP；
  - **工程**：状态持久化、HITL、可观测、安全、成本、评测。
- **核心口诀**：
  - *有循环才有智能，有工具才有行动，有记忆才有连续性，有安全边界才敢放它做事。*
  - *RRF 召回提率，Reranker 精排提质。*
  - *先想清要不要循环/多 Agent，再决定用多重的框架。*
- **面试加分**：能讲清"**为什么这样设计**"（权衡）比"会用 API"更重要。
